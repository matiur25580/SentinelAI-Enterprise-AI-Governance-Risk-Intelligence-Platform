# AI Risk Assessment Workflow

## Scope

SentinelAI stores evidence-backed, organization-scoped risk assessments for registered AI assets. A draft records the assessed system's intended use and scope, data sensitivity, autonomy, impact, likelihood, exposure, mitigation coverage, and evidence references.

## Versioned scoring heuristic

The API calculates scores server-side. Clients cannot submit or override scores.

- Context multiplier: `1 + ((dataSensitivity - 1) + (autonomyLevel - 1)) * 0.125`
- Inherent score: `likelihood * impact * exposure * contextMultiplier`
- Residual score: `inherentScore * (1 - mitigationCoverage / 100)`
- Bands: LOW (<= 40), MEDIUM (<= 100), HIGH (<= 175), CRITICAL (> 175)

The score is stored with `scoringVersion=sentinelai-risk-v1` so later formula changes do not silently rewrite historical assessments. Input dimensions are constrained to 1–5; mitigation coverage is 0–100. The database also enforces these bounds.

**Important:** this is a transparent project-specific triage heuristic, not a validated actuarial model, legal determination, NIST AI RMF score, ISO/IEC 42001 certification, or proof of regulatory compliance. Organizations must calibrate thresholds, document risk appetite, and obtain qualified human review before operational use.

## Lifecycle and separation of duties

1. An authorized OWNER, ADMIN, AI_GOVERNANCE, or AI_ENGINEER creates a DRAFT against an asset in their own organization.
2. The assessment creator submits the draft; it transitions to IN_REVIEW.
3. An OWNER, ADMIN, AI_GOVERNANCE, SECURITY_ANALYST, or COMPLIANCE_OFFICER independently approves or rejects it with a rationale.
4. A creator cannot review their own assessment. Completed decisions cannot be overwritten through the workflow.
5. Create, submit, approve, and reject events are written to the organization's append-only audit log in the same database transaction as the state change.
6. An asset with assessment history cannot be hard-deleted; retire it instead.

## API

All routes are prefixed by `/api/v1` and require a valid bearer access token.

| Method | Route | Access |
|---|---|---|
| POST | `/assets/:assetId/risk-assessments` | OWNER, ADMIN, AI_GOVERNANCE, AI_ENGINEER |
| GET | `/risk-assessments` | Authenticated organization member |
| GET | `/risk-assessments/:id` | Authenticated organization member |
| POST | `/risk-assessments/:id/submit` | Assessment creator |
| POST | `/risk-assessments/:id/decision` | OWNER, ADMIN, AI_GOVERNANCE, SECURITY_ANALYST, COMPLIANCE_OFFICER; never the creator |

List filters: `status`, `residualLevel`, `page`, and `limit` (maximum 100).

## Operational notes

- Apply the additive migration using the normal reviewed release process: `pnpm db:deploy`.
- Prisma Client is regenerated by `pnpm db:generate` / the CI build.
- Evidence entries are references or short descriptions, not file uploads. Do not put secrets, credentials, personal data, or raw prompts into evidence text.
- There is not yet a policy framework mapping, automated model evaluation, external evidence storage, notification delivery, or UI workflow for this capability.
